# Milestone 0 — toolchain trial

Date: 2026-10-19. Status: **in progress; hands-on acceptance pending**.

## Decision

Trial Godot 4.7.2 stable (official, ed1daf0bf) with GDScript and the Compatibility renderer. Unreal remains an unevaluated candidate, not a failed runtime benchmark. Do not proceed to combat implementation until this gate is accepted.

The Mac reports macOS 27.0.1. Epic's UE 5.8 requirements recommend Xcode 26.1.1, which Apple's support table lists for macOS 15.6–26.x. Xcode 27 compatibility with UE was not established. No full Xcode, Unreal, or Metal compiler was discovered. This makes a large Unreal installation an uncertain first step; the roadmap's smaller-toolchain fallback was used.

Sources checked:

- [Epic Mac requirements](https://dev.epicgames.com/documentation/unreal-engine/macos-development-requirements-for-unreal-engine)
- [Apple Xcode support matrix](https://developer.apple.com/xcode/system-requirements/)
- [Epic installation options and space estimates](https://dev.epicgames.com/documentation/unreal-engine/install-unreal-engine)
- [Official Godot macOS download](https://godotengine.org/download/macos/)

## Machine and footprint

- MacBook Pro: M3 Pro, 18-core GPU, 18 GB unified memory.
- Free system-volume space: approximately 68 GiB before setup, 63 GiB after downloads/export (other applications remain active; the full change is not attributable to this trial).
- Portable editor: approximately 337 MiB; editor archive: 176 MiB allocated on disk.
- Export-template download: 1,281,349,702 bytes for all platforms; only `templates/macos.zip` extracted and copied to Godot's local template directory.
- Workspace `.tools`: approximately 1.8 GiB including retained archives; development app: approximately 178 MiB.
- Godot signature verified successfully outside the restricted shell sandbox. Nothing was installed in `/Applications`; editor preferences/caches and the Mac export template use Godot's normal user Library directories.

## What works

- Project imports without script parse errors.
- Native graphical runtime starts using `OpenGL API 4.1 Metal - 91.7`, Apple M3 Pro, Compatibility renderer.
- Editor opens `arena.tscn`; a save command was sent. Full edit/save/close/reopen acceptance remains pending.
- Mac ARM64 development export succeeds. This local test app has no distribution signing/notarization; it is not a release artifact.
- Exported app visually verified through its window: arena walls, four pillars, target, blue player capsule, lighting/shadows, and HUD are visible.
- WASD movement, right-mouse orbit, and reset are implemented; Dean's manual responsiveness/collision check remains pending.
- Scene is generated by `arena.gd` at runtime, so the editor viewport initially shows an empty root. Press Play to see the arena. Moving static geometry into an editable scene can follow toolchain acceptance.

## Measurements

Initial separate editor-binary game process (not packaged): 5-second warmup followed by 60.0005 sampled seconds, 30,795 samples, average 513.25 FPS, p95 frame time 2.78 ms, maximum 34.96 ms. Reported window and viewport: 1920×1080, VSync disabled, automated orbit. This is script frame-delta timing, not a GPU profiler capture. Window visibility/occlusion was not monitored throughout; treat these numbers as preliminary.

Packaged benchmark: see `packaged-benchmark.log`. The app's window was visually inspected during this run and its HUD showed approximately 260 FPS at sample time. Final result: **152.15 FPS average, 6.94 ms p95 frame time, 134.98 ms worst frame**, 9,130 samples over 60.006 seconds. Reported window and viewport were 1920×1080. Other trial/editor processes were open during portions of this run; this is a baseline with interference, not a controlled performance certification. Average/p95 exceed the initial target, but the worst-frame spike needs a controlled repeat if it is noticeable during play.

Memory snapshot with editor open: system swap used approximately 14,606 MiB; `memory_pressure -Q` reported 33% system-wide memory free. There is no prelaunch baseline or peak-memory capture, so neither engine-attributable swap growth nor memory-pressure color is established. Close unnecessary applications before a controlled repeat. Editor cold-open and edit-to-play latency have not been measured reliably.

This is a primitive-only scene. It establishes no performance guarantee for animated characters, combat, effects, or final art.

## Reproduce and finish the gate

From the repository root:

```sh
./scripts/editor.command
./scripts/play.command
./scripts/benchmark.command
```

The benchmark runs the exported app for 5 seconds of warmup and 60 seconds of samples, then exits. Keep its window visible. It prints `TRIAL_RESULT` and stores JSON in Godot's `user://milestone0-result.json` directory. Scripts assume this workspace's downloaded editor/templates still exist; these binaries and builds are ignored by Git.

To rebuild after source changes:

```sh
.tools/Godot.app/Contents/MacOS/Godot --headless --path prototype --export-debug 'macOS Trial' ../builds/DuelTrial.app
```

Hands-on acceptance:

1. Open the editor, play, move with WASD, orbit with right mouse, and reset with R. Check walls/pillars stop movement and the camera remains usable.
2. Stop play, make a small reversible edit, save, close/reopen, and confirm the edit persists. Record cold-open and edit-to-play times.
3. Run the packaged app and confirm it feels responsive. Repeat the benchmark with its window visible and fewer background apps if results are erratic; record baseline/loaded memory and swap.
4. Record Dean's acceptance and choose Godot, adjust settings, or return to the Unreal setup investigation. Until then milestone 0 remains open.
